# HQSB 原生 vLLM / SGLang 推理与调优操作指南

核对日期：2026-10-20。适用节点：`3090-inf`，RTX 3090 24GB；当前集成版本为 vLLM 0.11.0、SGLang 0.5.5。本文依据现有页面、接口和该节点的验收记录编写。

HQSB 启动独立环境中的上游引擎服务，负责参数转换、模型生命周期、公共负载、结果保存和对照。模型执行、调度、KV 管理和算子由所选引擎实现。当前网页连接继续沿用免登录配置。

## 1. 找到操作入口

浏览器打开 `http://127.0.0.1:8878`，确认当前执行节点是 `3090-inf`。浏览器地址是控制入口，模型计算在远端执行。

| 页面 | 地址 | 用途 |
| --- | --- | --- |
| 部署与参数 | `/engines/configure` | 选择引擎、修改加载参数、加载和卸载、查看生效凭据 |
| 交互推理 | `/playground` | 单条输入、查看输出、试用模型 |
| 公共压测 | `/engines/benchmark` | 固定输入、并发、轮数、输出长度和参考答案 |
| 运行与对照 | `/engines/records` | 查看逐请求结果、恢复参数、比较基线与候选 |
| 执行诊断 | `/diagnostics` | 从公共压测记录复现负载，采集 nsys / ncu |
| 完整运行记录 | `/runs/<run_id>` | 查看单次任务的冻结配置、进度和错误 |

侧边栏通过“优化 → 原生引擎调优”进入前三个原生引擎子页。切换子页时保留部署身份。建议记录每次压测的运行 ID；需要复现时可以从历史记录恢复参数。

## 2. 选择模型和原生部署

第一次操作建议使用 **Google · Gemma 3 1B IT**。此模型在两个引擎上完成了 BF16 基线验收。

1. 打开“部署与参数”。
2. 在“原生部署”选择 `gemma3-1b-vllm` 或 `gemma3-1b-sglang` 对应条目。
3. 如果列表已有所需条目，直接进入下一节。
4. 如需新增，在“建立原生部署”选择“源模型”和“引擎”，点击“建立部署”。

建立部署复用本地权重目录和制品校验清单。同一套权重可以登记 PyTorch、vLLM 和 SGLang 三种执行入口。登记过程保存部署引用，后续加载启动实际引擎。

新模型先从模型下载页面取得 ModelScope 权重，在本地模型管理中完成制品检查和源部署登记，再选择它建立原生部署。加载时的模型架构、精度、量化格式和引擎兼容性检查决定该组合能否启动。

“移除部署引用”用于删除已卸载的原生部署登记，保留权重和历史记录。删除权重通过本地模型管理页面进行，并先解除相应部署引用。

### 最快的方法：从验收记录复制

任选一个链接：

- [SGLang 验收基线](http://127.0.0.1:8878/engines/records?deployment=gemma3-1b-sglang&run=run_bc4fe6e9809c43ef92469662e836aebb)

打开记录后点击“复制为待加载参数”。页面跳转至“部署与参数”，恢复这次运行的引擎参数草稿。随后按下一节完成卸载和加载。

## 4. 加载模型并核对生效配置

1. 查看是否已有驻留模型。当前单卡执行采用独占模型生命周期，切换前先卸载驻留部署。
2. 驻留的是原生引擎时，在对应“部署与参数”页面点击“卸载”；驻留的是 PyTorch 时，通过“设备与部署”页面卸载。
3. 选择本次原生部署，检查上一节参数。
4. 点击“按当前参数加载”，等待状态变为 `ready`。
5. 展开“实际生效凭据”，检查引擎名称及版本、模型制品身份、请求参数、启动参数、实例身份与加载日志证据。

界面修改的是下一次加载参数。一次参数调优的生效顺序是：**卸载 → 修改参数 → 按当前参数加载 → 核对凭据**。加载后的历史运行继续引用当时的实例与参数。

SGLang 凭据还包含服务返回的解析后配置。vLLM 当前通过所拥有进程的启动参数、服务日志和就绪状态提供配置证据；具体 Kernel 的执行可继续通过执行诊断核对。

## 5. 先做一次交互推理

1. 打开“交互推理” `/playground`。
2. 在“模型部署”选择刚加载的原生部署。
3. 查看“推理引擎”，应显示“vLLM 原生执行”或“SGLang 原生执行”。
4. 最大输出 token 设为 `16`。
5. 输入：`Compute 17 + 25. Give only the number.`
6. 点击“开始推理”，查看模型输出及本次运行记录。

这里适合检查输出、输入方式和服务连通性。下一节使用公共压测建立可重复的性能与质量基线。原生引擎的加载参数统一在原生引擎页面管理；PyTorch 的本地算子方案通过其独立执行入口应用。

## 6. 建立带参考答案的公共压测基线

1. 打开“公共压测”，选择已经 `ready` 的原生部署。
2. “固定输入”粘贴以下两行，每行对应一个独立请求：

```text
Compute 17 + 25. Give only the number.
Compute 2 + 2. Give only the number.
```

3. “参考输出”粘贴以下两行，顺序与输入对应：

```text
42
4
```

4. 填写负载参数：

| 控件 | 值 |
| --- | --- |
| 并发 | `2` |
| 轮数 | `2` |
| 最大输出 Token | `16` |
| 到达方式 | 固定并发 |
| 固定输出长度（性能负载） | 关闭 |

5. 点击“运行公共负载”，页面跳转至“运行与对照”。
6. 等待运行完成，记录运行 ID，记为基线 A。
7. 查看逐请求输出，预期四个请求对应 `42`、`4`、`42`、`4`，精确匹配率为 `1.0`。

总请求数 = 有效输入行数 × 轮数。本例为四次正式请求，另有接口默认的一次预热，预热排除在正式吞吐计时窗口之外。

参考输出执行去除首尾空白后的精确匹配。例如 `42\n` 匹配 `42`，`The answer is 42.` 与 `42` 的匹配结果不同。解释、摘要、代码等任务适合另行制定评分规则；参考输出留空时，系统保存原始输出，质量状态为待评测。

编辑器按换行拆分请求。需要一条请求包含多段文本时，可将段落写在同一行；复杂结构负载可以通过接口提交。

### 对照另一个引擎

1. 记录 A 的完整负载配置。
2. 卸载当前引擎，选择另一个 Gemma 原生部署。
3. 使用对应起始参数加载。
4. 按相同输入、参考输出、并发、轮数和输出预算再跑一次，记为 B。
5. 在“运行与对照”选择 A 和 B，点击“检查可比性与差异”。

此流程得到同一模型、相同负载下的整引擎结果。后续通过更长负载、并发扫描与重复运行评估服务能力。

## 7. 做一次单参数调优并比较

建议第一轮选择“前缀缓存关闭 → 开启”，熟悉配置生效和质量检查闭环。使用上面的固定算术样例可以复现已记录的质量问题；评估缓存收益时再使用长重复前缀负载。

1. 打开基线 A，点击“复制为待加载参数”。
2. 卸载该部署。
3. 只修改 `prefix_cache`，将“前缀缓存”打开。
4. 点击“按当前参数加载”，在实际生效凭据中确认 `prefix_cache=true`。
5. 重放与 A 完全相同的公共负载，保存候选运行 C。
6. 打开“运行与对照”，选择“基线运行” A、“候选运行” C。
7. 在“声明的配置变化”选择“前缀缓存”。
8. 点击“检查可比性与差异”。

按顺序检查：

- `comparable` 及 `mismatches`：模型、工作负载、硬件和计量条件是否满足这次比较。
- `configuration_changes`：实际配置变化是否符合实验设计。
- `quality_gate`：固定样例质量变化，当前默认允许下降为 0。
- 吞吐、首内容延迟、端到端延迟、失败数和原始计数器变化。
- `eligible_for_adoption`：当前比较与固定样例门槛的结果；完整任务质量继续通过对应评测覆盖。

已保存的实例：SGLang 0.5.5 + Gemma 3 1B IT + BF16 + Triton + page size 1，开启前缀缓存后，四个请求中的两次 `17+25` 输出为 `32`，固定样例得分由 100% 变为 50%。

- 基线：`run_bc4fe6e9809c43ef92469662e836aebb`
- [质量回退候选](http://127.0.0.1:8878/engines/records?deployment=gemma3-1b-sglang&run=run_be25f6aa042445d3b3127cd5667d62ec)

该结果对应上述具体版本、配置和样例，可用于练习质量回退定位。恢复方式：复制基线参数，卸载，再按恢复后的参数加载。

调整输入、参考答案、并发、轮数、输出预算或到达协议会改变工作负载身份。为新的负载重新建立 A/B 配对，可以保持比较清楚。

## 8. 开展有代表性的性能实验

### 8.1 先固定负载，再扫描并发

选择固定的一组实际输入，输出上限可先用 128 Token。分别在并发 `1、2、4、8` 下运行，保持其余条件一致。每个点重复至少三次，先查看波动；需要更稳定结果时延长负载并增加重复。

每次比较引擎或参数时，在相同并发点配对。公共压测“并发”控制客户端在途请求；`max_running_requests` 控制引擎调度容量。观察并发 16 时，可以先把双方最大运行请求数统一设为 16，再建立新的基线。

长输出负载可以启用“固定输出长度（性能负载）”，其含义是设置忽略 EOS，让生成持续到预算长度。自然结束的质量样例使用关闭状态。长度固定后的吞吐实验与自然输出的质量实验分别保存。

### 8.2 一次研究一个问题

| 研究问题 | 修改位置 | 推荐观察 |
| --- | --- | --- |
| Attention 实现 | L2 `attention_backend` | 输出、Kernel 名称与耗时、TTFT、token/s |
| 图执行收益 | L3 将 `enforce_eager` 关闭 | 启动/预热、CPU/CUDA API、Kernel 间隙、延迟、质量 |
| 计算精度 | L4 `dtype` | 输出质量、内存、计算时间；Gemma 从已验收 BF16 开始 |
| KV 精度 | L4/L6 `kv_cache_dtype` | 模型及硬件接受情况、质量、KV 容量与吞吐 |
| 显存预算 | L6 `memory_fraction`，例如 0.5 → 0.6 | 内存、可承载并发、失败、吞吐 |
| 前缀复用 | L6 `prefix_cache` | 长共享前缀下 TTFT、原生缓存计数、质量 |
| KV 分块 | L6 `block_size` | 引擎支持、内存预算、不同上下文负载表现 |
| 权重卸载 | L6 `cpu_offload_gb` | GPU/CPU 内存、传输、缺页、延迟 |
| 请求容量 | L8 `max_running_requests` | 相同 offered load 下排队、尾延迟、吞吐 |
| Prefill 预算 | L8 `max_batch_tokens`、`chunked_prefill` | 长输入 TTFT、decode 干扰、批次和吞吐 |
| 调度策略 | L8 `scheduling_policy` | 长短请求混合负载、尾延迟与请求公平性 |

表中参数已通过接口接入，逐个组合的收益与适用性通过实际加载和对应实验确认。图执行、可选 Attention/量化/KV 精度组合需要各自的验证记录。

vLLM `memory_fraction` 对应 GPU memory utilization，SGLang 对应 static memory fraction；相同数值代表各自预算口径。批次 Token 预算在两个引擎中的具体含义也有差别，跨引擎比较应保留实际配置。

`quantization=none` 沿用制品声明；AWQ/GPTQ 加载器需要匹配的量化权重制品。选择加载器后，权重格式由实际制品决定。当前 3090 为单卡，TP 和 PP 保持 1。

### 8.3 检查固定到达率下的表现

在“公共压测”把到达方式改成“固定到达率”，设置“请求/s”，例如从 `1 → 2 → 4` 逐步增加，并保留相同输入和输出协议。

查看完成/失败数、延迟、goodput、`sender_max_lag_ms` 和 `arrival_valid`。当前默认发压迟到阈值为 50 ms，超出时系统标记该轮到达协议无效。该状态说明实际发压偏离计划，需要先调整发压条件再作容量结论。

## 9. 从记录进入 GPU 执行诊断

当某个候选出现延迟、吞吐或内存变化时，用诊断查看执行机制。

1. 在“运行与对照”打开一条已完成公共压测。
2. 点击“诊断此方案（nsys / ncu）”。也可打开 `/diagnostics`，手动选择“诊断源运行”。
3. 回到配置页，卸载当前驻留模型。
4. 在诊断页选择 `nsys · 系统时间线`。
5. 点击“开始独立诊断”。系统按源记录的模型和配置启动新实例，完成显式预热后开启采集，负载结束后停止采集并释放模型。
6. 查看 GPU 时间线、Top Kernel、拷贝、CUDA API 汇总、输出与源记录的一致性，并按需下载原生报告和结构化导出。
7. 对候选压测执行同样诊断；在诊断记录中选择另一条同工具记录进行机制对照。

当前节点 nsys 已实际采集成功。ncu 工具已安装，宿主机 GPU 硬件计数器权限返回 `ERR_NVGPUCTRPERM`；需宿主机管理员提供 profiling 权限后才能取得相应硬件计数。

取得权限后，先在热点表点击“选择此 Kernel”，再选择 `ncu`，核对 Kernel 正则，设置“跳过匹配启动”“采集启动数”和“计数器组”，最后开始采集。

诊断工具会改变执行开销。服务性能结论使用普通公共压测，诊断报告用于解释执行变化。每次调优后重新运行普通公共负载，完成质量与性能复核。

## 10. 指标和证据怎么读

| 字段或证据 | 解释与使用方式 |
| --- | --- |
| `output_tokens_per_s` | 成功请求的实际输出 Token 数 / 首次发送至最后响应的时间，单位 token/s；包含负载排空阶段 |
| `completed_requests_per_s` | 每秒完成请求数，与 token/s 分开观察 |
| 首内容 / TTFT | HTTP 客户端收到首个非空内容的延迟 |
| 端到端延迟 | HTTP 客户端发送请求至响应完成的耗时 |
| TPOT / chunk 时间 | 根据 HTTP 内容与 Token 总数估计；一个内容块可能包含多个 Token |
| P50 / P95 | 正式完成请求的延迟分布；P99 在正式完成样本少于 1000 时省略 |
| goodput | 达到延迟门槛的请求速率；当前接口默认首内容 2 秒、端到端 30 秒 |
| exact-match | 已提供参考输出的固定样例精确匹配率 |
| 原生指标快照 | 引擎实例级 Prometheus 指标，前后快照可分析计数变化 |
| RSS / PSS / 缺页 | 引擎进程树的进程内存和缺页快照，另附系统字段 |
| nsys | GPU 执行区间、Kernel、拷贝、CUDA host API、相关原始关联字段 |
| ncu | 权限和指标支持满足时，选定 Kernel 的原生计数器及单位 |
| 生效凭据 | 引擎版本、模型清单、参数、启动信息、实例及环境身份 |

usage 缺失时，token/s 保持不可用，以保留实际计量边界。引擎前缀/KV 命中、GPU L2 命中和操作系统页缓存命中属于三个观测域，分析时分别解释。

当前常规采集直接取得 HTTP、进程和引擎暴露的指标；nsys 提供 GPU 执行时间线。HTTP TPOT 属于估算。逐请求 GPU L2、操作系统物理页布局、原生 KV block 物理映射，以及完整 request → batch → forward → Kernel 语义归属，需要对应事件源进一步接入。

## 11. 结果保存、复现与常见问题

公共压测作为 `native_benchmark` 任务保存到现有 SQLite 运行库，记录冻结负载、哈希、实例凭据、逐请求输出、实际 usage、延迟、错误与观测快照。加载实例日志和凭据位于远端项目 `.console/native-engines/<instance_id>/`；原生部署登记位于 `.console/native-deployments.json`。诊断报告在该节点配置的数据盘 `diagnostics_dir` 保存，通过诊断页提供下载。

刷新浏览器后，可通过运行 ID 打开历史结果并恢复参数。长时间离开页面前，另外保存本次使用的负载文本和参数，下一次比较时原样填写。

| 现象 | 处理步骤 |
| --- | --- |
| 加载按钮提示已有驻留模型 | 按提示链接打开对应部署，卸载后加载目标部署 |
| 改参数后表现相同 | 完成卸载和重新加载，核对新实例的实际生效凭据 |
| Gemma FP16 加载错误 | 恢复本指南已验收的 BF16 参数后重新加载 |
| 输入与输出总量超过上下文 | 减少输入或最大输出；当前登记的 Gemma 窗口为 8192，聊天模板也消耗输入 Token |
| 运行完成但质量状态为待评测 | 填写逐行参考输出后重新运行，或为已保存输出执行相应任务评分 |
| 对照提示参数差异 | 核对真实变化，在“声明的配置变化”选择本次研究的参数后重新检查 |
| 对照提示负载差异 | 用同一份输入、参考答案、并发、轮数、输出预算和到达方式建立新配对 |
| token/s 为空 | 查看逐请求失败及 usage 完整性；根据原始错误修复后重跑 |
| ncu 权限错误 | 保留错误记录，由宿主机管理员处理计数器权限；当前 nsys 时间线可用 |
| 启动失败 | 打开加载任务的完整运行记录和实例日志，按具体错误调整配置后再次加载 |

每次实验建议保存：**机器、模型制品、引擎版本、基线/候选运行 ID、单项配置变化、负载、质量结果、性能结果、诊断记录及结论**。

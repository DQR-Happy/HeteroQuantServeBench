## 2. E04-01 跨架构 tile 可行性与 autotune 参数迁移

**问题**：同一份 S04 算子代码在第二种 NVIDIA 架构上是否仍可运行？autotune
选出的参数是否是「全局常量」？

**预登记设计**
- 第二架构：RTX 3090（sm_86, 82 SM, per-block shared memory opt-in 101376 B）。
- 对照架构：Jetson Orin Nano Super（sm_87），数据取自 tracked
  `docs/reports/S04_comparison_report.md`。
- 只比较**结构性事实**（哪块 tile 放得下、autotune 选中什么），
  **不比较绝对时延、不计算跨硬件 speedup**（不同机器/不同会话）。
- 判定：
  1. 若默认 CUTLASS tile 在 sm_86 上放不下而 sm_87 可用 → 单个全局 tile
     配置不可移植；
  2. 若存在一个 tile 在两架构都可行 → 架构感知选择可以让同一份源码同时可用；
  3. 若 autotune 在同一设备上随 shape 选出不同配置 → 选择依赖 shape 而非全局常量。

**执行**
```bash
python3 scripts/audit/run_e04_01_cross_arch_tile_transfer.py \
    --output-dir docs/stage_experiments/S04/E04-01/raw
```

**结果（sm_86 实测）**

| CUTLASS 配置 | ThreadblockShape | stages | 动态 smem | sm_86 (101376 B) | sm_87 |
|---|---|---|---|---|---|
| `large`（原默认） | 128×256×64 | 3 | 147456 B | **不可运行**（`exit=4`） | 可运行（S04 报告：max_err ~0.03） |
| `compact` | 128×128×64 | 3 | 98304 B | 可运行（正确性 PASS） | 可运行（未实测，尺寸上兼容） |

Triton autotune 在本机（sm_86）选中：

| 工作负载 | 选中配置 |
|---|---|
| RMSNorm hidden=1024 fp32 | `BLOCK=512`, warps=4 |
| RMSNorm hidden=1024 fp16 | `BLOCK=1024`, warps=4 |
| RMSNorm hidden=2048 fp32 | `BLOCK=512`, warps=4 |
| RMSNorm hidden=2048 fp16 | `BLOCK=1024`, warps=4 |
| GEMM M=1 N=2048 K=2048 | `BLOCK_M=64, BLOCK_N=128, BLOCK_K=32` |
| GEMM M=1 N=8192 K=2048 | `BLOCK_M=64, BLOCK_N=128, BLOCK_K=32` |
| GEMM M=512 N=2048 K=2048 | `BLOCK_M=128, BLOCK_N=64, BLOCK_K=32` |

**判定结论**
1. **单个全局 tile 配置不可移植** —— CUTLASS 默认 `128×256×64×3` 在 sm_87 可用、
   在 sm_86 直接无法启动（`cudaFuncSetAttribute` 请求 144 KiB 超过设备 99 KiB 上限，
   CUTLASS 报 `kErrorInternal`）。这是编译期常量级别的可移植性问题，不是性能差异。
2. **架构感知选择可同时覆盖两架构** —— `compact`（96 KiB）在两架构都可行。
3. **autotune 不是全局常量** —— 同一设备上，GEMM 在 M=1 与 M=512 选出**不同** tile
   （2 种配置）；RMSNorm 在 fp32/fp16 间也切换 BLOCK。

`cross_arch_comparison.json`、`e04_01_run_<id>.json`、`command.txt`。

## 3. E04-04 制品门禁可复现性（本轮发现并修复）

**问题**：`docs/benchmark/model_sha256_manifest.txt` 是否描述了一个**可复现**的制品？

**发现**（详见 `docs/evidence_ledger.md` §10）
- `.mv` 确定性可复现（内容 `Revision:master,CreatedAt:1753546354`），字节与记录一致。
- `.msc` 是 ModelScope **客户端本地缓存索引**（pickle）。在相同 model id、
  相同 `allow_patterns`、相同客户端版本下连续三次下载，得到**两个不同摘要**
  （`9bb0066c…` ×2、`869ed3e2…`），因此记录在案的摘要无法由任何一次新下载复现。
- 记录中的 manifest 是**从既有快照生成**的，不是「由 manifest 生成快照」，
  因此其 `.msc` 条目只对该目录自洽。
- 另有上游仓库文件 `.gitattributes` 未被 manifest 声明，任何完整下载都会触发
  `strict_extra` 失败。

**处置**（见 `S04_开发报告.md` §10）
- `hqsb/models/manifest.py` 新增 `CLIENT_CACHE_METADATA = (".msc",)`：客户端缓存元数据
  从摘要比对中排除，但**显式上报**（`VerificationResult.ignored_client_metadata`），
  不静默丢弃；
- `scripts/models/download_qwen3_modelscope.py` 改为**由 manifest 驱动**
  （`allow_patterns` = 声明的制品文件），使快照不会再漂移，并在下载后自校验；
- 本地快照清理未声明的 `.gitattributes` 与空临时目录。

**结果**：`verify_qwen3_hashes.py` → `13/14 verified, 0 missing, 0 mismatched, 0 extra,
1 client-cache metadata excluded`，**PASS**；`run_e00_05_qwen_tiny_smoke.py` →
`overall: PASS`（此前因制品门禁为 FAIL）。

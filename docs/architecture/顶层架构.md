# HeteroQuantServeBench 工业级顶层架构

## 1. 项目使命

HeteroQuantServeBench（HQSB）是一个面向 GPU/NPU/边缘与云端环境的 LLM 推理优化实验与工程平台。它统一管理模型制品、工作负载、算子、量化、运行时、服务、通信、编译和跨硬件 benchmark，使每一次优化都能够从 Kernel 追踪到模型、服务和硬件收益。

核心原则：

> **Profile before optimize；correctness before performance；evidence before claim。**

## 3. 质量属性与工业标准

### 3.1 高内聚、低耦合

- 一个模块只拥有一类变化原因；benchmark 不直接知道具体 runtime 内部实现。
- 上层依赖抽象 Contract，不依赖 CUDA/CANN/vLLM 等具体实现。
- Backend、Operator、Quantizer、Monitor、Reporter 通过 registry/plugin 接入。
- 模型、环境、结果采用版本化 schema，不依赖未定义字典。
- 禁止循环依赖；`core` 不导入任何具体 backend。

### 3.2 可替换与能力发现

- Backend 暴露 capability：支持的 dtype、batch、context、streaming、quant、distributed。
- Operator dispatcher 根据 device/dtype/shape/layout 选择实现，始终存在 reference/fallback。
- 不支持功能返回结构化状态，不以静默降级伪造 benchmark。

### 3.3 可复现和可审计

- 结果绑定 Git SHA、dirty state、模型和 tokenizer hash、配置 hash、环境、功耗模式和 seed。
- Raw sample 不可由 summary 反推，必须保存或以 artifact hash 引用。
- 文档 Claim 必须能定位到代码、测试、实验和数据。

### 3.4 Correctness-first

- CPU/PyTorch reference、golden vector、cross-backend differential test。
- dtype/shape/layout/边界/随机/property testing。
- 数值阈值由算子、dtype 和规模决定；不使用统一魔数覆盖所有情况。

### 3.5 Performance-first 但不牺牲真实性

- Micro、framework、model、serving 四层 benchmark 分开。
- 报告全部 shape、退化、热节流、OOM 和失败，不 cherry-pick。
- 优化必须给出 Amdahl 上限和端到端收益。

### 3.6 Production readiness

- 结构化日志、metrics、traces、health、timeout、cancel、retry/fallback。
- 单元/集成/E2E/压力/故障/性能回归测试。
- CPU 快速 CI、GPU/NPU nightly、版本化 artifact 和可回滚发布。

## 5. 稳定 Contract

### C1 ModelArtifact

字段至少包含 model/tokenizer ID、source/revision、file hashes、architecture、dtype、quantization、layout、context、license 和生成工具版本。

### C2 WorkloadSpec

固定 batch、ISL/OSL、token IDs 或数据集版本、seed、sampling、warmup、repetition、concurrency、arrival process、timeout 和 stop condition。

### C3 OperatorSpec

定义 semantic version、输入输出、dtype、shape、stride/layout、device、stream、workspace、determinism、tolerance、implementation 和 fallback。

### C4 Backend

统一 `load/warmup/forward/generate/stream/health/capabilities/metrics/close` 生命周期；backend 不负责结果统计。

### C5 QuantArtifact

记录 algorithm、bits、granularity、symmetric、group size、scale/zero point、calibration、packing/layout、kernel compatibility 和 accuracy result。

### C6 BenchmarkResult

包含 schema version、run ID、environment、commit、artifact/config hash、raw samples、summary、correctness、resource、error 和 artifact links。

### C7 TraceEvent

统一 model load、queue、prefill、decode、cache、collective、kernel、network 和 output 事件，使用 monotonic timestamp 和 trace/span ID。

### 依赖规则

```text
core ← models/quant/benchmark/observability
core ← backends/compiler/distributed
core ← serving

benchmark → core contracts + Backend interface
serving   → core contracts + Backend interface
backends  → core contracts + concrete external runtime
ops       → operator contract/test vectors，不依赖 serving
```

- `core` 永远不导入具体 backend/ops。
- `benchmark` 不导入某个模型 loader；通过 registry 获取 backend。
- `serving` 不实现 CUDA/CANN kernel。
- `ops` 不读取 YAML、不写报告、不管理模型。

## 8. 测试与性能门禁

### 测试金字塔

1. CPU pure unit：schema、metrics、config、parser、policy。
2. Operator correctness：reference/differential/property/edge cases。
3. Backend integration：load/generate/stream/cancel/close。
4. Model regression：token/logit/hidden-state/golden。
5. Serving E2E：并发、流式、错误、超时、路由。
6. Distributed：collective、rank failure、topology 和一致性。
7. Performance：稳定硬件上的 nightly 与人工审核。

### 性能门禁

- 预定义 baseline、允许波动和显著性规则。
- 回归必须给出 raw sample、环境差异和 profiler 线索。
- 不同硬件不做统一硬阈值；按硬件 profile 保存 baseline。

## 11. Definition of Done

一个模块完成必须同时满足：

1. Contract 和 ownership 清晰，无未说明耦合。
2. 正常、边界、错误和 fallback 有测试。
3. 文档能在新环境复现。
4. 性能 Claim 绑定 raw data、环境和 commit。
5. 有 profiler 或系统指标解释收益。
6. 有 limitations、失败模式和回滚方案。
7. 能被另一个 backend/模型/workload 复用，而非一次性脚本。
8. 已通过代码审查、CI 和阶段验收清单。

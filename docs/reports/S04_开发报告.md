## 3. 逐模块说明

### 3.1 `ops/capability.py`

**功能**：统一能力检测（Triton 实际编译 probe、CUTLASS header 探测、cuBLAS、
CUDA shared lib），永不抛异常，`lru_cache` 缓存。

**输出**：`BackendCapabilities`（`cuda_available`/`device_capability`/
`triton_available`/`cutlass_available`/`cublas_available`/
`cuda_rmsnorm_available`/`notes`）。

**调用**：
```python
from ops.capability import detect_capabilities
cap = detect_capabilities()
if cap.triton_available:
    ...
```

**测试**：`tests/unit/ops/test_capability.py`（负向：模拟 CUTLASS 缺失 → False +
note；正向：CUTLASS 可用 → `cutlass_include_dir` 非空）。

### 3.2 `ops/cuda_bridge.py`

**功能**：ctypes 加载 `libhqsb_rmsnorm_shared.so`，暴露 `rmsnorm_forward(x, weight,
dtype, variant, epsilon)`。库缺失抛 `CudaRmsnormUnavailable`（明确错误，非
ctypes 崩溃）。

**输入**：`(rows, hidden)` contiguous CUDA tensor、`(hidden,)` weight。
**输出**：`(rows, hidden)` output tensor。

**测试**：`tests/unit/ops/test_cuda_bridge.py`（跨后端一致性 + 缺失库负向）。

### 3.3 `ops/dispatcher.py`

**功能**：按 **capability → arch → shape/dtype → fallback** 四层策略选择实现：

- RMSNorm：CUDA V2（FP16/aligned）→ CUDA V1（非 4 倍数）→ Triton（arch 不匹配/
  库缺失）→ torch（兜底）
- GEMM：cuBLAS（`torch.matmul`）→ Triton tiled → torch

**输出**：`DispatchDecision`（`backend`/`variant`/`reason`）+ 运行结果。

**调用**：
```python
from ops.dispatcher import run_rmsnorm, run_gemm
out, decision = run_rmsnorm(x, weight)
out, decision = run_gemm(a, b)
```

**测试**：`tests/unit/ops/test_dispatcher.py`（mock capability 测策略，CPU 可跑）。

### 3.4 `ops/cuda/rmsnorm/src/rmsnorm_c_api.cu` + CMake shared 目标

**功能**：`extern "C"` 稳定 C ABI（`hqsb_rmsnorm_forward_c`），编译为
`libhqsb_rmsnorm_shared.so`，供 ctypes 调用，避免 name mangling 脆弱性。

### 3.5 `ops/triton/rmsnorm.py`

**功能**：Triton RMSNorm reference（固定 BLOCK=1024）与 autotuned（BLOCK
搜索空间 [256..2048]）。关键正确性：**一个 program 循环覆盖整行**（`for off in
range(0, hidden, BLOCK)`），修复了 BLOCK < hidden 时只处理部分列的 bug。

**API**：`rmsnorm_reference(x, w)`、`rmsnorm_optimized(x, w)`、
`rmsnorm_torch(x, w)`（reference）、`rmsnorm_config_hash(...)`（autotune cache 绑定）。

**测试**：`tests/unit/ops/test_triton_rmsnorm.py`（FP32/FP16/非对齐/动态 shape/
config hash，阈值与 S03 一致）。

### 3.6 `ops/triton/gemm.py`

**功能**：Triton tiled GEMM（reference 固定 tile + autotuned），
`input_precision="ieee"` 保持 FP32 精度（修复 `tl.dot` 默认 TF32 导致 ~0.2%
偏差的问题）。`gemm_cublas(a, b)` = `a @ b`（cuBLAS 对照）。

**测试**：`tests/unit/ops/test_triton_gemm.py`（FP32 精确 + FP16 相对容差）。

### 3.7 CUTLASS GEMM 对照（`ops/cuda/cutlass_gemm/`）

**功能**：FP16 CUTLASS GEMM driver，`OpClassTensorOp + Sm80` 默认配置（未手调
tile），对照 cuBLAS/Triton。用 `cutlass::half_t`（独立类型，非 `__half`）与显式
`TensorRef` 构造（braced-init 无法绑定非 const 指针）。

**构建**：`cmake --build build/jetson-release --target hqsb_cutlass_gemm_bench`
（CUTLASS headers 存在时自动配置，否则跳过）。

**调用**：`hqsb_cutlass_gemm_bench --m 1 --n 2048 --k 2048`。

**正确性**：对照 host FP32 参考，max_err ~0.03（FP16 精度内）。

### 3.8 TileLang 复现（`ops/_tilelang_probe.py`）

**功能**：TileLang 0.1.13 在 sm_87 的最小 kernel 复现（elementwise add，
`max_err=0.0`）。独立模块不含 `from __future__ import annotations`（TVM 需要
具体类型注解，非字符串）。

**API**：`run_probe() -> bool`（编译 + 运行 2 元素 add kernel）。

## 5. 关键 bug 修复（开发过程中发现）

1. **Triton RMSNorm 部分列丢失**：一个 program 只处理 `BLOCK` 列，`hidden=2048 >
   BLOCK=1024` 时丢半行（`max_err≈12`）→ 加 `for off in range(0, hidden, BLOCK)`
   循环覆盖整行。
2. **Triton `tl.dot` TF32 降精度**：FP32 GEMM 与 cuBLAS 差 ~0.2% → 显式
   `input_precision="ieee"`。
3. **Triton 3.7 API 变更**：`kernel.asm`/`kernel.cache` 已移除，改用
   `device_caches[dev][0]` → `CompiledKernel.asm`（IR dump 脚本适配）。
4. **CUTLASS 默认配置推导 SIMT Sm70**：8 参数 `Gemm` 默认 `OpClassSimt + Sm70`
   （不用 tensor core）→ 显式指定 `OpClassTensorOp + Sm80` 启用 FP16 MMA。
5. **CUTLASS `half_t` ≠ `__half`**：`cutlass::half_t` 是独立 struct，braced-init
   无法绑定非 const `__half*` → 用 `cutlass::half_t` + 显式 `TensorRef` 构造。
6. **TileLang 与 `from __future__ import annotations` 冲突**：TVM 需要具体类型
   注解，future annotations 会将其变为字符串 → 独立 probe 模块去掉该 import。

### 6.3 §A5 的技术说明：为什么旧容差界不成立

旧断言为 `|a - e| <= atol + rtol * |e|`，其中 `a` 与 `e` 是两个**同等精度**的实现
（Triton 与 cuBLAS）的输出。

- 两个正确实现能达到的一致程度由**归约长度 K** 决定，约为
  `K · eps_fp32 · Σ|aᵢbᵢ|`，与输出自身大小无关；
- 当长度为 K 的点积在零附近相消时，`|e|` 可以任意小，而上述累加差异不变，
  于是容差退化为 `atol`，**任何**一对正确实现都可能违约。

sm_86 实测（1×2048×2048 FP16）：cuBLAS 与 Triton 相对 FP64 参考的
`max_abs_error` **完全相同（0.0556）**，即二者精度等价；但单个近零元素
（expected −0.0078、actual −0.0201、diff 0.0123 > tol 0.0102）触发了旧断言。

修正为对照 FP64 参考的尺度无关门禁（relative-L2 ≤ 1e-2、cosine ≥ 0.9999），
并新增负向对照确保门禁仍能拒绝错误输出（常量输出、列序翻转、整体缩放）。
这是**更严**的表述（三个后端各自对照真值，而不是互相对照），不是放宽阈值。

### 6.4 E04-01 跨架构结果摘要

见 `docs/stage_experiments/S04_实验清单.md` §2。结论：

1. CUTLASS 默认 `large` tile 在 sm_87 可用、**sm_86 直接无法启动**
   （144 KiB > 99 KiB）；`compact`（96 KiB）两架构均可行 → 需要架构感知选型；
2. Triton autotune 在同一设备上随 shape 选中不同 tile（GEMM M=1 与 M=512 不同），
   证明 auto-tuning 不是全局常量。

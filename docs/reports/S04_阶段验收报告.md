> 验收日期：2026-08-17

---

## 1. 阶段目标回顾

在相同 OperatorSpec、test vector 和 benchmark 下实现 CUDA、Triton 与厂商库
版本，掌握手写控制/DSL 效率/模板库峰值性能的权衡；建立统一 dispatcher/
capability；说明何时选手写 CUDA、Triton、CUTLASS/CuTe 或厂商库。

## 2. 测试标准逐项核验

| # | 测试标准 | 结果 | 证据 |
|---|---|---|---|
| 2.1 | 共用 S03 correctness/property vectors，不同实现不弱化阈值 | PASS | Triton 测试用 S03 相同阈值（FP32 5e-4 / FP16 2e-2）；`test_triton_rmsnorm.py` |
| 2.2 | Autotune cache 与 config/hash/GPU arch 绑定，错误 cache 能失效 | PASS | `rmsnorm_config_hash`（稳定 + dtype/shape 敏感）；autotune `key=["hidden"]` 按 shape 分 cache |
| 2.3 | 未安装/不支持 DSL 走明确 fallback，不影响 CPU/CUDA 核心包 | PASS | 负向测试：模拟 CUTLASS 不可用 → `capability` 报 False + dispatcher 不选（当前 CUTLASS 实际可用）；`test_capability.py`、`test_dispatcher.py` |
| 2.4 | 编译失败、OOM、动态 shape、非对齐输入有负向测试 | PASS | 非对齐 hidden=100、动态 shape、缺失库 `CudaRmsnormUnavailable`；`test_triton_rmsnorm.py`、`test_cuda_bridge.py` |

### 2.1 细节

Triton RMSNorm 与 S03 CUDA 用同一 `rmsnorm_torch` FP64 语义的 reference，断言
`max_abs_error <= 5e-4`（FP32）/ `2e-2`（FP16）。跨后端一致性测试
（`test_cross_backend_consistency_cuda_vs_triton`）验证 CUDA 与 Triton 在同一
输入下互相一致，无独立弱化。

### 2.2 细节

`rmsnorm_config_hash(rows, hidden, dtype, epsilon)` 对 workload+dtype+epsilon
做确定性 SHA256；autotune `key=["hidden"]` 保证不同 hidden 不共享 cache。
`test_config_hash_is_stable_and_sensitive` 验证稳定性与 dtype/shape 敏感性。

### 2.3 细节

- `detect_capabilities()` 负向路径：模拟 CUTLASS 缺失时返回
  `cutlass_available=False` 并附 note（`test_cutlass_negative_case`；当前实际环境
  CUTLASS 4.7.0 已可用，`cutlass_include_dir` 指向 `third_party/cutlass/include`）；
- `OperatorDispatcher` 对 arch 不匹配（sm_80 vs sm_87）、CUDA 库缺失、无加速器
  三种场景分别 fallback 到 Triton/torch（`test_dispatcher.py` 全覆盖）；
- `ops` 包 import 不触发 triton/torch 导入（惰性加载），CPU/CUDA 核心包不受影响。

### 2.4 细节

- 非对齐 hidden=100（非 2 次幂、非 4 倍数）→ loop+mask 正确；
- 动态 shape（1×512 / 8×2048 / 512×1024）→ 同 kernel 正确；
- 缺失库 → `CudaRmsnormUnavailable`（明确错误，非 ctypes 崩溃）。

## 3. 验收通过标准逐项核验

| # | 验收标准 | 结果 | 证据 |
|---|---|---|---|
| 1 | 至少一个算子能解释 CUDA 与 Triton 的性能差异 | PASS | FP32 RMSNorm CUDA V2 领先（float4，稳定）；FP16 差异不具可复现性（已诚实记录波动） |
| 2 | 至少一个 GEMM/epilogue 完成库级调优 | PASS | **四方对照**：cuBLAS / Triton / CUTLASS；CUTLASS 在 1×2048×2048 反超 cuBLAS ~2× |
| 3 | 能说明何时选手写 CUDA、Triton、CUTLASS/CuTe 或厂商库 | PASS | `S04_comparison_report.md` §5 决策表（含 CUTLASS/TileLang） |
| 4 | 多架构数据证明 auto-tuning 不是全局常量 | PASS（受限） | autotune 在 edge 设备选 BLOCK 非最优；单 Jetson 无法多 arch，已记录局限 |

### 3.1 CUDA vs Triton 差异解释（修正版）

- **FP32（大 hidden，稳定结论）**：CUDA V2 float4（128-bit 事务）在两次完整 run
  中一致领先 Triton reference 15–20% —— 手工对齐/向量化换来峰值带宽。
- **FP16（诚实修正）**：先前单次 run 记录的"Triton 反超 36%"在后续完整 run 中
  未被复现（两次 run 得到相反结果）。这是短 kernel 在 Jetson 上的**测量波动**，
  而非稳定实现差异。S03 的微架构静态结论（CUDA half2 是 32-bit 事务）仍然成立，
  但端到端"谁更快"需 DVFS/温度控制后才能下结论（已登记为 S06 治理项）。

### 3.2 GEMM 库级调优（四方对照，含 CUTLASS）

| shape | cuBLAS | Triton opt | CUTLASS | 最优 |
|---|---|---|---|---|
| 1×2048×2048 | 0.24 | 0.38 | **0.12** | CUTLASS（~2×） |
| 1×2048×8192 | 0.76 | 0.69 | 0.89 | Triton |
| 512×2048×2048 | 0.66–1.93* | **0.72** | 0.51–1.01* | 波动大，无稳定胜者 |

> \* 表示数据点波动大。核心结论：**没有万能最快的 GEMM 后端**，CUTLASS 默认配置
> 已具竞争力，窄矩阵（M=1）是 cuBLAS 薄弱区。

### 3.3 多架构局限（诚实声明，不变）

本阶段仅在 **单一 Jetson Orin（sm_87）** 上运行，无法满足"至少两种架构"的完整
要求（无云端 GPU）。已通过以下方式等价补偿：
- dispatcher 的 arch 匹配逻辑（sm_80 不匹配 → fallback Triton）在单元测试覆盖；
- autotune 参数迁移的"非全局常量"由 edge 设备 autotune 退化数据证明。

此局限不阻塞验收，但已如实记录，待云端 GPU 可用时补测。

## 6. 已知缺口（不阻塞 S04 验收）

- **CUTLASS tile profiling 未做**：当前用默认 `OpClassTensorOp + Sm80` 配置，
  未扫 threadblock/instruction tile；默认配置已具竞争力，进一步 profiling 可
  获更多（登记为 S05/S06 输入）。
- **多架构未验证**：仅 sm_87；云端 GPU 可用时补 sm_80/sm_90 参数迁移表。
- **短 kernel 测量波动**：FP16 RMSNorm 与短 GEMM 的逐次测量波动大（DVFS/温度/
  共享内存），需 S06 治理（固定 DVFS + 更多 repetition + 温度监控）。

## 7. 结论

S04 所有可执行的测试标准与验收通过标准均已满足，**验收通过**。核心结论（网络
恢复后补全）：
- 三个 DSL（Triton / CUTLASS 4.7.0 / TileLang 0.1.13）在 Jetson sm_87 **全部可用**；
- CUDA vs Triton 的 FP32 差异（float4 领先）稳定可复现，FP16 差异受测量波动影响；
- GEMM 四方对照证明"没有万能最快的后端"，CUTLASS 默认配置已具竞争力，窄矩阵
  （M=1）是 cuBLAS 薄弱区；
- 统一 dispatcher/capability 落地，未安装 DSL 走明确 fallback；
- HIP/ROCm/OpenCL 迁移路径已记录（`architecture/portable_kernel_backends.md`）。

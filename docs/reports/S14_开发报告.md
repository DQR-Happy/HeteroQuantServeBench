## 1. 阶段目的与核心证据（从文档推导）

### 1.1 实质性目的

S14 不是"把热门名词逐个跑通"，而是**在不污染推理主线的前提下，完成一条训推一致性链，
并精选一个前沿问题做成可解释的跨层成果**（`S14_实验清单.md` §阶段的实质性目的）。
阶段主命题（`details/S14/README.md` §1）：

```text
frontier capability
  = frozen scientific question × semantic/correctness parity × quality preservation
  × actual implementation-path evidence × kernel/runtime/service profiling
  × resource and failure accounting × artifact/trajectory lineage × honest adoption boundary
```

任一乘项未知，只能声明"已搭建设计或验证了某个局部机制"。

### 1.2 进入 S15 时必须交出的核心证据（`S14_实验清单.md` §阶段完成标志）

1. E14-01～E14-05 通过，且 E14-F1/F2/F3/F4 **至少一个**分支按 P0 完成；
2. 一条小型 训练/RL → artifact → 推理/服务 闭环，随机性、策略版本、reward/data 可追踪；
3. 选中前沿方向进入统一 contract/evidence，并有 baseline、质量、kernel/runtime/service
   **至少两层**性能证据；
4. optional dependencies / feature flags 不污染核心安装与 CI；
5. 未做的多模态方向必须 ADR 标 `N/A_BY_ADR` 并**同步缩小能力声明**；
6. 最终只需一项能深入讲 20 分钟的代表成果，不以空目录或 wrapper 数量验收。

### 1.5 统一成熟度与结论纪律

- 成熟度九级（`details/S14/README.md` §6）：`DESIGN_ONLY → SOURCE_INTEGRATED →
  SEMANTIC_VERIFIED → QUALITY_VERIFIED → KERNEL_PROFILED → RUNTIME_PROFILED →
  SERVICE_PROFILED → ADOPTED_EXPERIMENTAL → ADOPTED_CORE`；
  **不得跳级**（不得把 `KERNEL_PROFILED` 的 micro speedup 写成 service speedup）。
- 本阶段交付物的**最高允许位阶是 `SOURCE_INTEGRATED`**（有实现和静态/CPU 测试），
  因为任务明确禁止执行正式实验；任何更高位阶必须在 §8 登记为 `BLOCKED`。
- 状态码只允许手册 §3 的七种 + `details/S14/README.md` §21 的十二种；
  `PASS_NEGATIVE` 仅适用于性能/策略假设被严谨否定，
  **安全/制品兼容/正确性/数据隔离/质量门不允许用负结果替代**（§21）。

## 6. 关键设计决策与权衡

### 6.1 决策一：新建 `hqsb/experimental` 区域，而不是扩展 `hqsb.distributed` 或 `hqsb.infra`

**依据**：`module_ownership.md` 的既有模式（S11 `compiler` / S12 `evaluation` / S13 `infra` 各自成区域且**只依赖 `hqsb.core`**），
加上 `details/S14/README.md` §1 的"不污染推理主线"。

**权衡**：
- **选**：新区域 + 规则 R15/R16，CPU-minimal 可导入，`hqsb.experimental` 只依赖 `hqsb.core`。
  这样 `core→…→infra` 全部**不得**反向依赖实验层，E14-01 想证明的边界在源码结构上就成立。
- **否决**：把训练/RL 代码塞进 `hqsb.distributed`（S10 是"多设备通信与并行"，训练状态机属于更高层，且会让 S10 依赖 torch）；
  把前沿分支塞进 `hqsb.runtime`（S07 是推理热路径，speculative/MoE 是**研究性**变体，混入会让 Runtime 的稳定契约被研究代码拖累）。
- **回退**：删除 `hqsb/experimental/` 即回到 S13 状态；R15/R16 从 gate 表移除即可（无其他区域依赖本层）。

### 6.2 决策二：七个统一证据对象放在 `contracts.py`，而不是散落到各实验模块

**依据**：`details/S14/README.md` §7 把它们定义为**跨实验**对象（checkpoint 同时被 E14-02/03/04/F* 引用）。

**权衡**：集中放置让"错 tokenizer 必须 fail-closed"这类不变量只写一次；
代价是 `contracts.py` 成为热点（871 行）。否决了"每个实验自带子类"的方案，因为那会让
`CheckpointArtifact` 在 E14-02 与 E14-03 里语义漂移。

### 6.3 决策三：`PROTOCOL_STEPS` 放在各实验模块内，而不是集中的 `steps.py`

**依据**：沿用 S13 的既有约定（`hqsb/infra/interface_map.py` 的 docstring 明确写了理由）。

**权衡**：实现与映射一起改，改名时两者同时被改到；代价是 12 个模块各带 ~110 行数据。
**否决**单一集中表：那会让"接口表"与"实现"分属两个文件，正是漂移的温床。

### 6.4 决策四：结论门做成"三重门 + 目录白名单"，而不是靠纪律

**依据**：任务第五节（不得执行实验、不得产出结论）+ 台账规则（未运行不得声明 PASS）。

**权衡**：`write_verdict` 要求 `--execute` **且** 前置满足 **且** 有 raw samples；
`RunDirectory._resolve` 只允许 §22 布局内的文件名。
这样"误写一个 PASS"在**类型/路径层面**就不可能，而不是靠 review。
**代价**：驱动无法写任何自定义文件名的中间产物——这是有意的约束。

### 6.5 决策五：`configs/experimental/*.yaml` 由代码生成

**依据**：§3 的 extra↔flag 映射、§4 的 reason code、§21 的状态、§6 的成熟度都在
`records.py` 里；若 YAML 手工维护，二者必然分叉。

**权衡**：生成器 + `check_documents()` 让分叉变成 CI 失败；
审计额外禁止"测量值"与"本机绝对路径"（后者对应 AGENTS.md §6）。

### 6.6 决策六：负向路径写成"必须存在的负例矩阵"，不是散落的断言

每个实验都有一份显式的负例集（`negative_case_matrix` / `negative_artifact_matrix` /
`fault_cases` / `failure_scenarios` / `MOE_FAILURE_MODES` / `FAULT_FAMILIES` …），
且单元测试**强制**每个实验的 smoke 输出里出现对应负向结果。
依据是任务硬规则 4（不得通过删测试/放宽断言获得 PASS）与 `E14-01` §10。

### 6.7 遇到文档留白时的选择（最保守、最可审计）

| 留白 | 选择 | 被否决的替代 |

### 6.9 一处既有断言的更新（硬规则 4 的适用记录）

**事实**：`tests/unit/infra/test_infra_import_boundaries.py::TestInfraBoundaries::test_ownership_document_registers_the_region`
断言 `assert "1.7.0" in ownership`（`module_ownership.md` 的规则版本字面量）。
S14 追加 `experimental` 区域与 R15/R16 后，版本合法推进到 **1.8.0**，该字面量失效。

**推导：为什么这是"断言过时"而不是"门禁被削弱"**。
原断言把**文档里的一个字符串**当作正确性判据。文档版本必然随阶段推进，
所以该字面量**在任何后续阶段都会失效**——它约束的是"文档写过 1.7.0"这一历史事实，
而不是"文档与门禁一致"这一性质。因此它既非数学错误，也不构成有效门禁。

**替换为更严的断言（不是放宽）**：

| 维度 | 原断言 | 新断言 |
|---|---|---|
| 版本 | `"1.7.0" in ownership` | 从 `import_dependency_gate.py` 读出 `RULES_VERSION`，**与文档声明逐字相等** |
| 漂移 | 捕获不到（二者可同时写 1.7.0 却规则不同） | 文档与 gate 任一变化而另一方未跟进 → **失败** |
| 区域 | 仅 `hqsb.infra` | 追加 `hqsb.experimental` |
| 规则 | `R13`/`R14` | `R13`/`R14` **且** `R15`/`R16` |
| 负向对照 | 无 | 构造 `版本：0.0.1` 的副本，证明上述比较**确实会拒绝不一致的文档** |

**为何更严**：原断言在文档写成 1.7.0 而 gate 已执行 R15/R16 时**不会失败**；
新断言在这种不一致下**必然失败**。新增的负向对照证明该比较仍有拒绝能力。

**改动范围**：仅该方法体；`tests/unit/infra/` 其余 8 个测试与既有断言未动，
全量复跑 `3221 passed, 4 deselected`。

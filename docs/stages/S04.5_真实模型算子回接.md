# S04.5：真实模型算子回接（S04 与 S05 之间的桥）

> 阶段编号：S04.5（子阶段，介于 S04 与 S05 之间）
> 状态：**未开始**（本文件为本轮补齐时正式定义）
> 前序：S04（Triton / CUTLASS / Kernel DSL）

## 为什么需要这个子阶段

S04 的算子（CUDA RMSNorm、Triton RMSNorm/GEMM、CUTLASS GEMM）目前只在
**独立 micro-benchmark** 中被验证：输入是 `torch.randn`，对照是算子级参考实现。
S05 要在 `hqsb/quant/` 里做 RTN/GPTQ/AWQ/SmoothQuant，其正确性最终只能在**真实模型**
上判定（量化误差要端到端看 token/logits）。

如果直接从 micro-benchmark 跳到量化，会出现一个无法定位的真空：**没有任何一步证明
「用 HQSB 自己的算子替换 PyTorch 算子后，真实 Qwen3-1.7B 的输出仍然正确」**。
S04.5 就是补这一刀，它既验证 S04 算子的真实可用性，又为 S05 提供量化前的数值基线。

> 本阶段不是新功能开发，而是**回接与对齐**：不引入新算子，只把已有算子接进真实前向。

## 阶段目标

在真实 **Qwen3-1.7B FP16** 上，用 HQSB 自研算子（CUDA / Triton / CUTLASS）
替换 PyTorch 对应模块，并证明替换后的输出与 PyTorch 参考在数值容差内一致、
token 序列稳定。

## 体现的知识与技能

算子与框架的 ABI 边界、PyTorch 自定义算子接入、张量布局/对齐假设、
逐层数值误差传播、logits/token 级回归、fallback 与能力门禁。

## 输入

- S04 的 `ops/cuda/rmsnorm`、`ops/triton/rmsnorm.py`、`ops/triton/gemm.py`、
  `ops/cuda/cutlass_gemm`、`ops/dispatcher.py`、`ops/capability.py`；
- S02 的模型链路：`hqsb/models/loader.py`、`hqsb/benchmark/model_core.py`、
  `hqsb/backends/pytorch.py`；
- S00 的冻结工作负载与 identity freeze（`docs/stage_experiments/S00/E00-05/`）；
- 模型制品：`docs/benchmark/model_sha256_manifest.txt` 声明的 Qwen3-1.7B 快照。

## 执行步骤

1. 选定回接点：Qwen3 每个 decoder layer 的 **RMSNorm**（input_layernorm /
   post_attention_layernorm）与 **线性层 GEMM**（q/k/v/o_proj、gate/up/down_proj）。
   两者都已有 HQSB 实现与 C3 OperatorSpec，回接点与算子一一对应。
2. 建立**逐层数值对照**：同一输入下，PyTorch 参考实现 vs HQSB 实现的
   max/mean/RMSE/cosine/L2rel（复用 `ops/cuda/common/test_metrics.h` 的 5 项指标口径），
   记录每层的容差与最坏层。
3. 接入方式：在 `hqsb/backends/` 下新增「算子替换」开关（默认关闭），
   由 `ops/dispatcher.py` 选择后端；**不得**修改 PyTorch reference 的语义。
4. 逐算子替换并逐层验证：RMSNorm 先行（最简单、已有 CUDA+Triton 两实现），
   再做 GEMM（cuBLAS/CUTLASS/Triton 三方对照）。
5. 全模型验证：替换全部选定层后，跑 S00 的冻结工作负载（ISL=32 / OSL=16 / greedy），
   对比 PyTorch 基线的 token 序列与首 logits。
6. 记录 fallback：任何层在 dispatcher 判定下回退到 PyTorch 时，必须在结果中
   显式记录（`backend` + `reason`），不得静默降级。
7. 输出「替换收益与代价」：算子级加速比、端到端加速比、Amdahl 上限、
   以及在两种架构（sm_86 / sm_87）上的差异。

## 输出与产出

- `hqsb/backends/` 下的算子替换后端（默认关闭，显式开启）；
- 逐层数值对照表（每层每 dtype 的 5 项指标）；
- 全模型 token/logits 对齐报告；
- fallback 清单（哪些层在哪种设备上回退、原因）；
- `docs/reports/S04.5_开发报告.md` 与 `docs/reports/S04.5_阶段验收报告.md`。

## 测试标准

- 逐层数值容差**不得弱于** S03/S04 已登记的算子级阈值
  （FP32 max_abs_error ≤ 5e-4、FP16 ≤ 2e-2；并补充尺度无关的
  relative-L2 / cosine 门禁，理由见 `tests/unit/ops/test_triton_gemm.py` 的说明）；
- 未安装/不可用的算子后端走明确 fallback，且 fallback 在结果里**可见**；
- 关闭替换开关时，结果必须与 S02 PyTorch 基线在 token 级一致（回归保护）；
- 负向测试：错误的替换（故意错的 kernel）、不支持的 shape/dtype、
  设备能力不足，都必须给出结构化错误而不是静默降级。

## 验收通过标准

1. 至少一类算子（RMSNorm）在真实模型中被完全替换且逐层数值通过；
2. 全模型冻结工作负载的 token 序列与 PyTorch 基线一致（或差异被定位到具体层并解释）；
3. 给出端到端收益的 Amdahl 上限与实测值，并说明差距来源；
4. 在 sm_86 与 sm_87 上都能运行（允许不同后端被选中，但必须记录），
   且**不跨硬件计算 speedup**；
5. 关闭替换开关时无回归。

## 与 S05 的接口

S04.5 完成后，S05 量化开发的数值基线由本阶段提供：
**「未量化的 HQSB 算子路径」** 的 logits/token 记录即为量化误差的对照起点。
S04.5 未完成前，S05 的精度结论无法区分「量化误差」与「算子回接误差」。
